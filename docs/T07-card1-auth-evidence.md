# T07 카드 1 — 인증 구현 설명 및 검증 기록

## ① 무엇으로 붙였나 (C91·C92)
- 인증 방식: 외부 인증 서비스
- 서비스: Supabase Auth
- 클라이언트 라이브러리: `@supabase/supabase-js` 2.x
- 근거: `index.html`의 `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2`
- 참고: 2.x는 메이저 버전 범위이며 배포 소스는 2.117.3으로 고정함

## ② 선택 이유와 대안 (C93)
- 현재 구현의 설계 이유: 비밀번호 저장·검증을 자체 구현하지 않고 Supabase Auth에 맡기며, 사용자별 접근은 PostgreSQL RLS로 제한
- 비교 가능한 대안: 직접 인증 서버 구현. 비밀번호 해시·세션 관리·보안 패치 부담이 더 큼
- **주의:** 위 대안은 기술적 비교 대상이며, 개발 당시 실제로 검토했는지는 사용자 확인 전까지 단정하지 않음

## ③ 어디를 어떻게 고쳤나
- `index.html`에 이메일/비밀번호 가입·로그인·로그아웃 구현
- 로그인한 사용자의 `user_id`로 데이터 조회 제한
- 기존 이메일 중복 가입에 대해 오해를 주는 가입 완료 문구 개선
- 새 계정에 기존 Plan이 없을 때 단일행 조회 오류 및 잔류 화면 상태 개선
- Supabase `public` 8개 T07 테이블에 사용자 소유권 RLS 정책 확인

## ④ 접근 차단 및 인증 검증
- 비로그인 로컬 HTML 접속 시 로그인 화면만 표시: 사용자 캡처 확인 (C97)
- 중복 가입: 배포 화면에 '이미 가입된 이메일입니다. 로그인해주세요.' 표시; Supabase 사용자 목록에 기존 이메일 1개 확인 (C98)
- 잘못된 비밀번호와 미가입 이메일: 양쪽 모두 'Invalid login credentials' 표시 (C99)
- A 계정의 기존 운동 데이터 유지 및 B 계정 데이터 0건 확인
- 미완료 검증: 배포 주소 비로그인 직접 접근, 실제 A↔B 요청의 읽기·수정·삭제 거절, 로그아웃 전후 동일 토큰 요청

## ⑤ AI와 나
- AI에게 맡긴 일: 인증 구현 코드 검토·수정 및 연결 서비스의 설정·배포 상태 점검
- 내가 판단한 일: 중복 가입 안내를 실제로 수정하도록 요구하고 실사용 화면으로 검증
- 따르지 않은 제안: 문제를 수정하지 않고 '수정 대상으로 기록'만 하자는 제안을 수용하지 않음

## ⑥ 아직 못 막은 것 / 한계
- 배포된 프런트엔드에서 새로운 계정의 Plan 생성 후 전체 흐름은 아직 실사용 검증되지 않음
- 로그아웃 후 기존 JWT는 만료 전까지 서버 측에서 유효할 수 있음; 세션 삭제와 JWT 즉시 폐기는 다름
- 사용자 간 직접 요청 차단은 RLS 정책 존재 확인과 별도로 실제 사용자 토큰 기반 테스트가 필요함
- 현재 JSON 내보내기에는 T07 연구 설정과 규칙 변경 테이블이 포함되지 않음
